# Megatron GRPO rollout 内存

共置 GRPO 会交替执行训练、权重导出、生成和参考模型推理。仅凭 GPU 利用率不能区分
这些阶段；模型 CPU 副本、优化器状态、固定内存暂存区和文件系统页缓存也会占用主存。

以下选项默认关闭，不改变奖励、KL 系数、序列长度、并行配置或 checkpoint 内容与保存频率。

## 将冻结的参考模型缓存到磁盘

`--reference_model_cache_dir /absolute/private/scratch` 为全参数 GRPO 启用进程内使用的
文件缓存，同时需要 `--use_vllm true --vllm_mode colocate --offload_model true`。
缓存要求参考参数在 CUDA 上初始化，因此 `use_cpu_initialization` 必须保持默认值 `false`。

启动前创建 scratch 目录。目录必须属于训练用户、禁止其他用户写入，路径中不能包含
软链接。使用 ext4、XFS 或 Btrfs 等磁盘文件系统，不能使用 tmpfs。只有显式设置
`--reference_model_cache_allow_nfs true` 才允许 NFS；共享存储仍需容纳全部 rank 的缓存，
并可能带来显著的 I/O 延迟。

可用空间检查在 ext4、XFS 或 Btrfs 上按本节点训练进程数计算缓存及预留空间，在显式
启用的 NFS 上按全局 rank 数计算。分布式缓存创建要求启动环境显式设置
`LOCAL_WORLD_SIZE` 或 `LOCAL_SIZE`，且与训练器的本地进程数一致；若两者都设置，
数值也必须一致。缺失或格式错误会被拒绝，不会根据 GPU 数量猜测。例如，56 rank、
每节点 4 个进程的任务在每块本地磁盘上按 4 份缓存计算，在共享 NFS 上按 56 份计算。
此保守检查使用当前可用磁盘空间，不会跨 rank 预留容量。

缓存在首次卸载参考模型时建立，因此位于 checkpoint 加载之后。冻结权重按有界块复制
到私有映射文件。后续卸载会检查文件内容与参数清单，再复用映射；恢复时等待设备复制
完成后，才建议系统回收这些文件的缓存页。这样可避免额外保留一份完整的匿名 CPU
参考模型副本。页回收建议本身不能证明实际释放了多少 RAM。

仅接受布局受支持的普通、连续、冻结参数。策略模型与参考模型别名以及不支持的存储
布局会明确报错。策略模型、教师模型和优化器保持原有路径。此缓存属于可丢弃的本地
状态，不是 checkpoint，也不能用于冷恢复；新进程不会接管旧缓存。文件包含模型权重，
必须采用与模型相同的访问保护。仅在所属进程终止后清理保留的 scratch 文件。

启用缓存选项时，无 KL 的 GRPO（`--beta 0`）会同时跳过参考模型分配和缓存创建；
该模式不能同时指定参考 checkpoint 或 adapter。未启用该选项时，原有模型准备路径不变。

## 释放恢复后的策略模型 CPU 副本

`--release_model_cpu_cache true` 在原生策略模型恢复完成后释放冗余 CPU 参数缓冲区，
要求全参数 GRPO 和模型卸载。实现会检查参数与梯度缓冲区已经驻留，并在释放 CPU
复制源之前同步设备复制。模型值、参数别名、冻结参数和优化器状态保持不变。

下一次卸载会重新分配 CPU 缓冲区。该选项以减少缓冲复用换取更低的主存保留量，
不保证提速。如果所用 PyTorch 提供对应 API，还会释放非活跃的固定内存分配器缓存。

## Rollout 专家并行

对于支持的 MoE 模型，通过现有引擎选项传入 JSON 布尔值：

```shell
--vllm_engine_kwargs '{"enable_expert_parallel": true}'
```

该值会显式传递给共置 vLLM 引擎，不会消费或修改调用方的选项字典。字符串 `"true"`
会被拒绝。Rollout 专家并行与 Megatron 训练并行是分别配置的。

## 验证范围

CPU 回归覆盖缓存内容及损坏拒绝、所有权与存储检查、恢复与释放顺序、配置边界和
引擎参数转发。这些检查不能证明完整模型的 GPU 容量、吞吐、分布式 checkpoint 恢复
或训练质量。在新任务中启用前，需在目标 GPU 拓扑上验证集成后的代码。

正在运行的任务继续使用原来的不可变源码包；推送此分支不会更新它们。
